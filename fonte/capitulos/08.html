O que é (e o que não é) arquitetura de software

Para começar Uma cidade que cresce sem plano vira um labirinto em que qualquer obra trava o trânsito. Um software também pode “funcionar” hoje e ser um pesadelo para mudar amanhã. Arquitetura é o plano que evita isso.

Na aula Fundamentos de Arquitetura de Software para Backend, do canal Fernanda Kipper, arquitetura é a organização fundamental de um sistema: componentes, relações entre eles e os princípios que guiam sua evolução. Martin Fowler prefere “o entendimento compartilhado que os desenvolvedores experientes têm do sistema”. O vídeo VOCÊ NÃO SABE ARQUITETURA DE SOFTWARE (veja esse vídeo), apoiado no livro Arquitetura Limpa, de Robert C. Martin, a define pelo que ela não é: não decide se o sistema funciona (há muitos sistemas funcionando com arquiteturas horríveis) nem se resume a pastas. Seu objetivo é tornar o sistema fácil de entender, manter e implantar. Um caso citado: mudar o texto de um endpoint levou duas semanas porque ninguém achava a classe responsável.

Há decisões estruturais (monólito ou microsserviços, eventos, serverless, nuvem, banco) e decisões de design de código (Clean Architecture, Hexagonal, MVC, padrões, interfaces). A Lei de Conway (1967) lembra que sistemas copiam a estrutura de comunicação da organização; como times mudam, é mais estável dividir o sistema por responsabilidades de negócio (autenticação, checkout, estoque).

A mesma aula organiza o vocabulário em seis conceitos, que voltam ao longo do capítulo:

  • Stateful × stateless (com ou sem memória do cliente). Pergunta: o servidor precisa lembrar de mim? Exemplo: um caixa de padaria que não lembra de você; a cada compra você mostra a comanda de novo.
  • Síncrono × assíncrono. Pergunta: preciso da resposta agora? Exemplo: no balcão, o café sai na hora; a revelação de fotos avisa quando ficar pronta.
  • Acoplamento (o quanto uma parte depende da outra). Pergunta: essa dependência faz sentido? Exemplo: a escola exigir o pagamento para matricular é normal; mexer no caixa do financeiro, não.
  • Idempotência (repetir não muda o resultado). Pergunta: e se o pedido chegar duas vezes? Exemplo: apertar três vezes o botão do elevador chama um elevador só.
  • Cache (cópia guardada perto para ganhar tempo). Pergunta: posso usar uma informação um pouco velha? Exemplo: o cardápio impresso pode ser de ontem; o saldo da conta, não.
  • Restrições. Pergunta: quanto dinheiro, tempo e gente eu tenho? Exemplo: uma padaria de bairro não precisa de um sistema de rede de supermercados.

Linguagens e fundamentos

Para começar O computador só entende código de máquina, então toda linguagem precisa de um tradutor: alguns traduzem tudo antes, outros na hora, outros um pouco de cada. Esta seção mostra esses modelos, o que são tipos e os erros clássicos de Java, JavaScript e Python.

Modelos de execução

  • Bytecode + máquina virtual (Java, Kotlin, C#): o javac gera bytecode portável, que a JVM interpreta e compila em tempo de execução (JIT). A JVM também cuida da coleta de lixo.
  • Compilação nativa (Swift, Rust, C/C++, em geral via LLVM): código de máquina para uma arquitetura específica, rápido, mas não portável.
  • Transpilação (TypeScript → JavaScript): o tsc verifica tipos e emite JS; os tipos desaparecem em tempo de execução.

Tipagem: dois eixos independentes

Estática × dinâmica diz quando o tipo é verificado (compilação em Java, TypeScript, Go; execução em Python, JavaScript). Forte × fraca diz quanto a linguagem aceita conversões implícitas. Python é dinâmica e forte ("1" + 1 dá erro); JavaScript é dinâmica e fraca ("1" + 1 === "11"). Dizer que Python é “fracamente tipado” é um erro comum.

A aula CURSO DE TYPESCRIPT para INICIANTES | Aprenda Typescript na Prática mostra o ganho prático: o editor pega res.jon(...) antes de virar erro 500 em produção. Recomendações: "strict": true, evitar any e usar union types de literais. Um contraponto vem do post Existem linguagens melhores pra programar com LLMs?, do blog AkitaOnRails: num experimento com sete linguagens e quatro modelos de IA, a tipagem forte não reduziu os reparos, porque os erros eram de regra de negócio. O que mais ajudou foi uma suíte de testes. Conclusão do autor: “disciplina vence compilador e vence linguagem”.

Memória: stack, heap e garbage collector

A stack guarda os frames de chamada (variáveis locais e referências) e é liberada quando o método retorna; recursão sem fim termina em StackOverflowError. O heap guarda os objetos, e o garbage collector libera os que ninguém mais alcança. O vídeo Entendendo COLETOR DE LIXO DO JAVA (memória Heap, Stack, Garbage Collector) compara os coletores da JVM: Serial (simples, pausas longas), Parallel (throughput), G1 (padrão desde o Java 9, meta de pausa curta) e ZGC/Shenandoah (pausas abaixo de 1 ms, mais CPU). A escolha é sempre throughput × latência; faça profiling antes de trocar.

Front-end

Para começar O front-end é a vitrine: tudo o que o usuário vê no navegador. Ela é feita de HTML (estrutura), CSS (aparência) e JavaScript (comportamento). Veremos como uma página chega à tela, CSS, React e um pouco de design de interface.

Como a web funciona

A aula CS50x - Lecture 8 - HTML, CSS, JavaScript, de Harvard, resume a base. Roteadores encaminham pacotes IP (IPv4 tem 32 bits, ~4,3 bilhões de endereços; IPv6, 128 bits). O TCP acrescenta portas (80, 443) e retransmissão. O DNS traduz nomes em IPs. O HTTP define verbos (GET, POST, PUT, PATCH, DELETE) e códigos de status:

CódigoSignificado

413 / 429Payload grande demais / Too Many Requests (rate limiting)

O navegador transforma o HTML numa árvore, o DOM, que o JavaScript manipula em resposta a eventos. Lição de segurança da aula: validação no cliente é conveniência, não proteção. Quem valida de verdade é o servidor.

Você sabia? O código HTTP 418 “I'm a teapot” nasceu de uma piada de 1º de abril, a RFC 2324, de 1998, que descrevia um protocolo para controlar cafeteiras. Ele nunca foi usado a sério, mas muitos frameworks o implementam até hoje.

CSS: Flexbox, Grid e responsividade

Flexbox é unidimensional: justify-content alinha no eixo principal e align-items no secundário; trocar row por column inverte os eixos, o erro mais comum de iniciante. Grid é bidimensional: a unidade fr divide o espaço livre, grid-template-areas nomeia regiões e repeat(auto-fill, minmax(200px, 1fr)) cria colunas responsivas sem media queries.

Responsividade importa porque a maior parte do acesso à internet no Brasil é pelo celular. O TUTORIAL COMPLETO CSS MEDIA QUERY - Criando layouts responsivos na PRÁTICA recomenda mobile first (estilos base para o celular, min-width para telas maiores), poucos breakpoints padronizados (768 e 1024 px) e evitar larguras fixas.

.cards { display: grid; grid-template-columns: 1fr; gap: 1rem; }   /* mobile first */
@media (min-width: 768px)  { .cards { grid-template-columns: repeat(2, 1fr); } }
@media (min-width: 1024px) { .cards { grid-template-columns: repeat(4, 1fr); } }

Entre os frameworks, o Bootstrap oferece componentes prontos (btn btn-primary, grid de 12 colunas) e o Tailwind é utility-first, com uma classe por propriedade (mt-4, md:flex) e um build que mantém só as classes usadas.

React: hooks e dados remotos

O React monta a tela com componentes e redesenha só o que muda. Os hooks principais:

  • useState: só o setter avisa o React. Quando o novo valor depende do anterior, use setCount(prev => prev + 1).
  • useEffect(fn, deps): roda quando as dependências mudam; o return é o cleanup. Em desenvolvimento, o StrictMode monta duas vezes de propósito, o que explica logs duplicados.
  • useContext evita passar props por vários níveis; hooks customizados (useAlgo) encapsulam lógica reutilizável.

Buscar dados com useEffect + fetch obriga a reimplementar loading, erro, retry e cache em cada tela. O TanStack Query resolve com useQuery e useMutation, e invalidateQueries recarrega a lista após uma mutação. Micro front-ends (vídeo Microfrontends Explicado Simples: A Arquitetura que Está Mudando o Frontend) dão deploy independente a cada time, ao preço de complexidade; como microsserviços, só valem para times grandes.

O tutorial Criando APLICAÇÃO COMPLETA e ESCALÁVEL com Angular + Edge Computing mostra o problema clássico das SPAs: sem JavaScript nada aparece, o que prejudica o SEO. A solução é Static Site Generation: cada página vira HTML estático, servido a partir da borda de uma CDN.

Back-end e APIs

Para começar Se o front-end é o salão, o back-end é a cozinha, e a API é o garçom: o cardápio com regras pelo qual um programa faz pedidos a outro. Veremos estilos de API, validação, cobranças em dobro, tempo real e a infraestrutura na frente do servidor.

Estilos de API

Para o vídeo What Is an API? Types, Uses, & AI Integration, na era da IA a API é o “canudo” que leva dados até o modelo e permite que ele aja. Três estilos dominam:

  • REST: cada coisa tem um endereço, e os verbos HTTP dizem o que fazer. Simples e fácil de pôr em cache. Bom para APIs públicas. Como pedir um prato pelo número do cardápio.
  • GraphQL: um endereço só, e o cliente diz quais campos quer, nem mais nem menos. Cache mais difícil. Bom para telas com necessidades variadas. Como montar o próprio prato no self-service.
  • gRPC: chama uma função de outro servidor como se fosse local, com mensagens binárias pequenas (Protocol Buffers). Rápido, porém difícil de depurar. Bom entre serviços que você controla. Como o interfone direto entre a cozinha e o caixa.

O vídeo O que fazer quando RESTful não for suficiente faz uma observação que vale para o capítulo todo: quem programa com IA precisa saber quando pedir gRPC, filas ou CQRS, porque a IA dificilmente vai sugerir sozinha.

DTOs e validação

Um DTO (Data Transfer Object) é um contrato simples que valida e transporta dados (vídeo DTOs, o que é e porque usar). Use DTOs separados para entrada (CreateUser tem password) e saída (UserResponse nunca tem). Passar o corpo da requisição direto para o ORM permite mass assignment: o atacante envia "is_admin": true. Validar e-mail mostra o limite das regex (Como Validar Email do Jeito Certo!): uma regex completa da RFC 5322 é gigante e arrisca ReDoS. A receita é regex simples, biblioteca no back e, sempre, um e-mail de confirmação.

Idempotência e double submit

Uma operação é idempotente quando repeti-la tem o mesmo efeito de executá-la uma vez. Pela semântica HTTP, GET, PUT e DELETE devem ser; POST não. Mas os vídeos Todo DEV precisa entender isso: IDEMPOTÊNCIA e Como sistemas evitam requisições duplicadas alertam: não presuma pelo verbo. Clique duplo, retry após timeout e rede instável causam double submit, e as defesas se empilham:

CamadaTécnicaLimite
TelaDesabilitar o botão após o cliqueQuem quiser consegue burlar
HTTPPost/Redirect/Get (303)Só evita o reenvio ao apertar F5
ServidorChave de idempotência (um “número do pedido”) guardada num lugar compartilhado, como Redis ou bancoÉ preciso definir o que é “repetido” e por quanto tempo
BancoRestrição UNIQUEExige um campo realmente único, como o CPF

Para cadastros, redirect + unique bastam. Para pagamentos e estoque, a chave de idempotência é obrigatória, e nunca na memória local de um servidor só.

CORS

CORS diz se uma página de um site pode ler respostas de outro (vídeo O que é CORS? Análise frontend e backend). Ele existe só no navegador; curl e serviços entre si não têm “erro de CORS”. Requisições não simples disparam um preflight OPTIONS, e o * não vale com cookies. CORS não substitui autenticação nem proteção contra CSRF (cookies SameSite, tokens).

Proxy reverso, CDN e rate limiting

Um proxy reverso é a recepção do prédio: fica na frente dos servidores e cuida de roteamento, TLS, cache e balanceamento. O vídeo Apache vs NGINX contrasta o Apache (processo ou thread por conexão no modelo clássico) com o Nginx, criado em 2004 para o “problema C10K”, com poucos workers orientados a eventos. Em APRENDA NGINX DO ZERO | Curso de NGINX em 1 HORA, a pegadinha clássica é a barra final do proxy_pass, que decide se o prefixo é repassado:

upstream frontend { server localhost:3000; server localhost:3001; }  # round-robin
server {
  listen 80;
  location /     { proxy_pass http://frontend; }
  location /api/ { proxy_pass http://localhost:8000/; }  # barra final remove /api
}

Uma CDN é uma rede de depósitos perto do usuário: servidores de borda guardam cópias de arquivos estáticos e buscam na origem só no miss (vídeo O que é uma CDN? Para que serve a CDN?).

Rate limiting limita requisições por cliente num intervalo. No vídeo Rate Limiter | Explicação Completa, o autor conta um ataque cujo único objetivo era gerar custo num sistema serverless. Os algoritmos clássicos são fixed window (simples, mas permite rajada dupla na virada), sliding window (preciso, usa mais memória), token bucket (permite rajadas controladas) e leaky bucket (saída constante). A resposta padrão é 429 com Retry-After, e a mesma ideia serve para orçamentos de tokens por usuário em apps com LLM.

Estado global, connection pooling e event loop

Estado global no back-end gera bugs difíceis de reproduzir: o vídeo Como Uma Requisição Contamina Outra mostra uma variável current_user compartilhada entre requisições paralelas. Prefira funções puras, contexto por requisição e injeção de dependência.

Abrir uma conexão com o banco é caro (TCP, TLS, autenticação). Com connection pooling (Como 1.000 Requests Usam 20 Conexões | Connection Pooling), mil requisições compartilham, por exemplo, 20 conexões. O pool é criado fora do handler, e o release vai num finally. Em serverless, use um pool externo (PgBouncer, RDS Proxy).

const pool = new Pool({ max: 20 });          // uma vez, no módulo
app.get('/users/:id', async (req, res) => {
  const client = await pool.connect();
  try { res.json((await client.query('SELECT * FROM users WHERE id=$1', [req.params.id])).rows[0]); }
  finally { client.release(); }
});

Até console.log pesa: no Node, escrever em arquivo ou terminal é síncrono e atrasa o event loop. Nos testes do vídeo Console log pode TRAVAR a sua aplicação (explicação), cem logs por requisição derrubaram a vazão de um servidor de ~1,3 milhão para ~71 mil requisições no mesmo intervalo. Use logs assíncronos e estruturados (Pino).

Por fim, cada dependência externa traz riscos de cadeia de suprimentos (o caso xz, de 2024), atualizações quebradas e imagens maiores. A regra de O custo de usar muitas dependências: não instale uma biblioteca para uma única função; fixe versões com lockfile e audite no CI.

Bancos de dados

Para começar Um banco de dados é o arquivo-mestre da empresa: guarda as informações de forma organizada e segura. Há bancos relacionais, como planilhas com colunas fixas consultadas em SQL, e NoSQL, como fichas livres. Veremos garantias, distribuição, busca, evolução do esquema, cache e sharding.

Relacional × documento, ACID × BASE

O MySQL organiza dados em tabelas com esquema; o MongoDB guarda documentos JSON flexíveis (MySQL vs MongoDB). Os vídeos ACID e BASE explicado de forma simples e Como Escolher o Banco de Dados Correto pra sua Aplicação | System Design & Arquitetura de Software mostram que a escolha começa pelas garantias. ACID: atomicidade (a transferência debita e credita, ou nada), consistência (o estoque nunca fica negativo), isolamento (duas compras do último item: uma falha) e durabilidade (o confirmado sobrevive a um crash). BASE troca correção imediata por disponibilidade e escala, com consistência eventual. Pagamentos, estoque e ingressos pedem consistência forte; likes, analytics e recomendações aceitam a eventual. Na prática as fronteiras se misturam: o MongoDB tem transações ACID e o DynamoDB oferece leitura consistente sob demanda.

CAP e PACELC

Quando um banco roda em várias máquinas e a rede entre elas cai, cada lado precisa decidir: continua atendendo com dado talvez velho ou para até a linha voltar? O teorema CAP (Brewer, 2000) diz que, durante uma partição, é preciso escolher entre consistência e disponibilidade. Um banco prefere ficar indisponível a mostrar saldo errado (CP); uma rede social prefere mostrar curtidas atrasadas (AP). O PACELC (Abadi, 2012) completa: sem partição, a escolha diária é entre latência e consistência (replicação síncrona é consistente e lenta; assíncrona, rápida e eventual).

BancoClassificação usualMecanismo
Cassandra / ScyllaDBPA/EL (ajustável)Cada consulta escolhe quantas réplicas confirmam (ONE, QUORUM, ALL)
MongoDBPC/EC (padrão)Replica set com eleição de primário
DynamoDBPor requisiçãoConsistentRead true/false
CockroachDB, SpannerPC/ECAs réplicas votam antes de confirmar (Raft/Paxos)

Com fator de replicação RF, se os nós lidos (R) e escritos (W) somam mais que RF, toda leitura cruza com uma réplica atualizada. Dois erros comuns: confundir o “C” de ACID (invariantes) com o do CAP (todas as réplicas devolvem a última escrita), e chamar o Postgres de “CA”. Um nó só não sofre partição; com réplicas, a escolha volta a existir.

Índices e Full-Text Search

Um índice é como o índice remissivo de um livro. O vídeo O QUE NINGUÉM TE ENSINOU SOBRE BUSCAS INTELIGENTES NO BANCO DE DADOS! mostra que LIKE '%termo%' busca substrings (“anel” acha “panela”) e, com o curinga no início, não usa índice B-tree: lê a tabela inteira. O Full-Text Search tokeniza, remove stopwords, reduz palavras ao radical (stemming) e monta um índice invertido.

-- PostgreSQL
CREATE INDEX idx_fts ON products USING GIN (to_tsvector('portuguese', name || ' ' || description));
SELECT * FROM products
 WHERE to_tsvector('portuguese', name || ' ' || description) @@ plainto_tsquery('portuguese', 'capa dura');

A lição dos números do vídeo: sem o índice, o FTS foi mais lento que o LIKE (139 ms contra 4,9 ms); com o índice GIN, caiu para 0,3 ms. Para relevância de grande e-commerce, use um motor dedicado (Elasticsearch/OpenSearch); para substrings tolerantes a erro, a extensão pg_trgm.

ORMs, SQL injection e migrações

Uma ORM traduz objetos em SQL (user.save()). O vídeo Como ORMs Mentem pra Você lista o que ela esconde. O principal é o N+1: um loop que acessa order.customer.name dispara uma consulta por pedido. A solução é eager loading (select_related no Django, include no Prisma, JOIN FETCH no JPA). Inspecione o SQL gerado com EXPLAIN ANALYZE e use SQL puro nas consultas críticas. Contra SQL injection, a defesa são consultas parametrizadas (WHERE id = $1), não “sanitizar” strings (O que é SQL injection e como resolver).

Rodar ALTER TABLE à mão em produção não é revisável nem reproduzível (Como Fazer Migrações de Banco de Dados do Jeito Certo). Migrações ficam no repositório, passam por PR e o banco registra qual versão aplicou. Para mudar sem downtime, use expand/contract: adicione a coluna nova, escreva nas duas, faça o backfill em lotes, mude as leituras e só depois remova a antiga. Já o database branching (Pare de quebrar o banco em produção: Aprenda Database Branching) dá a cada branch de código uma cópia copy-on-write do banco de staging, que só duplica os blocos alterados.

Cache

Cache é deixar o sal ao lado do fogão em vez de buscá-lo na despensa. Funciona por causa das ordens de grandeza de latência citadas em CACHE-ASIDE: Escalabilidade, Performance e Arquitetura de Software pra Mandar Bem na Entrevista!: RAM ~100 ns, SSD ~100 µs, disco rígido ~10 ms. Mesmo pela rede, uma leitura no Redis costuma ser bem mais rápida que uma consulta com joins.

No cache-aside, a aplicação lê o cache; no miss, lê o banco e grava no cache com TTL. Alternativas: write-through (grava nos dois, cache sempre atual, escrita mais lenta) e write-behind (grava no cache e persiste depois, com risco de perda). Armadilhas: o cache stampede (milhares de misses quando uma chave quente expira; use lock ou TTL com jitter) e cache local em várias instâncias, cada uma com uma versão diferente.

O caso da Timeline do Facebook (ARQUITETURA BACKEND DO FACEBOOK | System Design) mostra que cache sem estratégia não basta: a solução combinou desnormalização, separação entre dados quentes e frios e um agregador rodando na própria máquina do banco, levando a computação até os dados.

Sharding

Réplicas de leitura escalam leituras, mas não escritas nem volume. Quando o primário não aguenta, vem o sharding: os dados são fatiados entre bancos independentes. O vídeo Aprenda a Escalar Bancos de Dados Usando SHARDING | System Design & Arquitetura de Software propõe uma ordem: escala vertical, índices, cache, otimização de queries, réplicas e, por último, sharding.

  • A shard key precisa de alta cardinalidade, distribuição uniforme e afinidade (usuário numa rede social). created_at por ano concentra a carga no shard atual (hotspot).
  • hash(key) % N remapeia quase tudo quando N muda; o consistent hashing move só ~1/N das chaves.
  • Desafios: o “problema da celebridade”, consultas entre shards e transações distribuídas, que viram Sagas com compensações.

Design de código: orientação a objetos bem feita

Para começar Orientação a objetos organiza o programa em peças que juntam dados e comportamento, como blocos de LEGO. Peças bem desenhadas podem ser trocadas sem desmontar o castelo. Esta seção mostra os sintomas de um código apodrecendo e três ferramentas: SOLID, Object Calisthenics e padrões de projeto.

Object Calisthenics

As nove regras de Jeff Bay (The ThoughtWorks Anthology, 2008) são exercícios, não leis, comentados em Separando Dev Júnior de Dev Senior (Object Calisthenics). As mais úteis: um nível de indentação por método; não usar else (guard clauses, retornar cedo); encapsular primitivos em Value Objects que se autovalidam (Email, CPF); um ponto por linha (Lei de Demeter: peça order.getCustomerZipCode() em vez de navegar a cadeia); e evitar getters/setters (Tell, Don't Ask). Regras como “no máximo duas variáveis de instância” são consideradas exageradas.

// Anêmico: a regra mora num "Service"
if (product.getPrice() > 50) product.setPrice(product.getPrice() - 10);
// Rico: a entidade protege a própria regra
product.applyDiscount(Money.of("10.00"));

Nunca use float para dinheiro: 0,1 + 0,2 ≠ 0,3 em ponto flutuante binário. Use BigDecimal, centavos inteiros ou um tipo Money.

Acoplamento: um espectro, não um pecado

Para Augusto Galego, em Quando Vale a Pena Desacoplar Seu Código?, o método “receita de bolo” que salva, cobra, reserva estoque e envia e-mail em sequência é ótimo para um MVP. Cada nível de desacoplamento (interface + injeção → fila → pub/sub) compra resiliência e paga em indireção. Três frases dele: “abstração é útil quando abstrai alguma coisa” (UserService + UserServiceImpl sem segunda implementação é cerimônia); “fila não dá velocidade, dá vazão”; e IAs tendem a desacoplar ao máximo até software simples, então dê pushback.

Arquitetura de aplicação

Para começar Agora olhamos a montagem inteira. O coração do sistema (as regras de negócio) não deveria depender da “roupa” que ele veste (framework, banco, provedor de pagamento). Veremos as arquiteturas que protegem esse núcleo, a escolha entre monólito e microsserviços e dois padrões avançados: CQRS e Event Sourcing.

Clean Architecture e Hexagonal

As duas fazem as dependências apontarem para dentro. A Clean Architecture (Robert C. Martin) organiza o código em anéis: entidades, casos de uso, adaptadores e frameworks. A Hexagonal (Ports and Adapters, Alistair Cockburn, 2005) tem um núcleo que define portas (interfaces de entrada e de saída) e adaptadores que as implementam, como mostra a figura a seguir. Os vídeos Me de 30 minutos para aprender Arquitetura Limpa e Hexagonal e Arquitetura Hexagonal | Explicação de um Dev Sr. mostram as duas na prática: no fundo, é DIP + Adapter aplicados à aplicação inteira.

Ganha-se testabilidade (casos de uso rodam com adaptadores em memória) e liberdade para trocar fornecedores sem tocar no núcleo. Paga-se em arquivos e indireção. Não é organização de pastas: o que importa é o núcleo depender só de interfaces que ele mesmo define.

Monólito, monólito modular e microsserviços

Um monólito é uma unidade de deploy. Um monólito modular mantém o deploy único, mas cria fronteiras internas com contratos mínimos: no exemplo de Aprenda MONOLITO MODULAR ANTES de MICROSERVIÇOS, matrículas só chama cobrancas.isConfirmed(pedido), e cobranças pode trocar de provedor sem afetar ninguém. Microsserviços separam também deploy, processo e banco. A pergunta-chave, citada em Quando usar Monolitos vs Microserviços, é: “que benefício justifica trocar uma chamada de função por uma chamada de rede?”. O custo vem em autenticação entre serviços, tracing, latência, consistência entre bancos e infraestrutura.

A Shopify segue como monólito modular famoso, e a Amazon Prime Video relatou em 2023 que voltar um pipeline de monitoramento para um processo único cortou o custo em 90%. Dividir mal produz um monólito distribuído, o pior dos dois mundos. O consenso: comece pelo monólito modular e extraia serviços quando a dor for real.

CQRS e Event Sourcing

Numa biblioteca, o balcão de devoluções (escrita) e o catálogo de consulta (leitura) têm necessidades diferentes. O CQRS (Command Query Responsibility Segregation), explicado em CQRS: O PADRÃO ARQUITETURAL QUE TODO PROGRAMADOR PRECISA CONHECER!, separa o modelo de escrita do de leitura. Faz sentido quando há assimetria: uma página de produto agrega dezenas de tabelas, enquanto a escrita toca uma ou duas. Réplicas de leitura ajudam, mas não são CQRS, porque mantêm o mesmo modelo.

O ponto delicado é a sincronização. Gravar no banco e depois publicar no Kafka cria o dual write: se a segunda operação falha, os lados divergem. As soluções são o CDC (ler o log de transações do banco) ou o Transactional Outbox (gravar o evento numa tabela na mesma transação e publicá-lo depois). O resultado é consistência eventual; validações críticas, como saldo, consultam a fonte da verdade.

Event Sourcing (EVENT SOURCING: APRENDA A CONSTRUIR SISTEMAS QUE VÃO ALÉM DO CRUD, CQRS e EVENT SOURCING | Design de Software Maduro) leva a ideia ao limite: o estado é a soma de eventos imutáveis (ContaAberta, DepósitoFeito…), como um extrato. Um UPDATE apaga a história; um evento a preserva. Projeções geram modelos de leitura, snapshots evitam reprocessar tudo e o replay permite reconstruir o passado, por exemplo para estornar tarifas declaradas indevidas. Correções são eventos inversos, nunca deleções. Ambos são decisões de domínio (auditoria, finanças), não modismos: num CRUD simples só multiplicam a complexidade.

Disponibilidade e o cálculo dos “noves”

O SLI é a medida real (fração de requisições boas), o SLO é a meta interna (99,9% em 30 dias) e o SLA é o contrato com o cliente, geralmente mais frouxo. A diferença 1 − SLO é o error budget: enquanto houver orçamento, o time arrisca deploys; quando acaba, prioriza confiabilidade. O downtime permitido é (1 − disponibilidade) × período:

DisponibilidadeDowntime/anoDowntime/mês (30 d)
99%3,65 dias7,2 h
99,9%8,76 h43,2 min
99,99%52,6 min4,32 min
99,999%5,26 min25,9 s

O que mais pesa é a composição. Componentes em série multiplicam disponibilidades: LB (99,99%) × API (99,9%) × banco (99,95%) ≈ 99,84%, pior que qualquer um isolado. Réplicas em paralelo combinam como 1 − (1 − A₁)(1 − A₂): duas de 99% dão 99,99%, como mostra a figura a seguir. Mas só se as falhas forem independentes: duas réplicas na mesma zona, com o mesmo bug, caem juntas.

A disponibilidade também se escreve A = MTBF / (MTBF + MTTR). Na prática, reduzir o tempo de recuperação (MTTR) com alertas, rollback rápido e runbooks costuma ser mais barato que evitar toda falha.

DevOps, entrega e operação

Para começar O código ainda precisa chegar aos usuários e continuar funcionando. DevOps une quem desenvolve e quem opera, como uma linha de montagem com inspeções automáticas e sensores que avisam quando algo quebra. Veremos contêineres, CI/CD, nuvem e monitoramento.

Contêineres e Docker

Uma imagem é um sistema de arquivos em camadas, imutável, descrito por um Dockerfile. Um contêiner é um processo isolado que compartilha o kernel do host, e não uma VM. O Compose descreve vários serviços (app, banco, cache) para desenvolvimento local reproduzível.

FROM node:22-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci                 # camada cacheada enquanto o lockfile não mudar
COPY . .
RUN npm run build

FROM node:22-alpine        # imagem final sem ferramentas de build
WORKDIR /app
COPY --from=build /app/dist ./dist
COPY --from=build /app/node_modules ./node_modules
USER node                  # não rodar como root
CMD ["node", "dist/server.js"]

Boas práticas: copiar o manifesto antes do código, multi-stage, imagens base enxutas e fixadas, .dockerignore e nenhum segredo na imagem.

CI/CD

A integração contínua roda build, lint e testes a cada push. A entrega contínua deixa cada versão pronta para produção; a implantação contínua a publica automaticamente (CD é delivery ou deployment, não “development”). O vídeo Como Eu Começo Um Projeto do Zero recomenda publicar o “Hello World” em produção no primeiro dia, com deploy a cada merge na main, para que os problemas de “funciona na minha máquina” apareçam quando ainda são baratos.

# .github/workflows/ci.yml (esqueleto)
on: [pull_request, push]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: npm }
      - run: npm ci && npm run lint && npm test
  deploy:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps: [ { uses: actions/checkout@v4 }, { run: ./scripts/deploy.sh } ]

Regras de arquitetura e segurança devem morar no pipeline (análise estática, policy as code), não numa wiki: o objetivo é “tornar o caminho certo o mais fácil”. A infraestrutura também vira código (IaC: Terraform, manifestos do Kubernetes), versionado e revisado. Na nuvem, o serverless “escala pelo cartão de crédito”, então rate limiting e alarmes de cobrança são obrigatórios.

Observabilidade

Observabilidade é entender o sistema pelos sinais que ele emite, como o painel de um carro: logs estruturados (com correlation id e sem dados sensíveis), métricas e traces distribuídos (OpenTelemetry). Os golden signals do Google SRE são latência (em percentis p95/p99, nunca só a média), tráfego, erros e saturação. O monitoramento sintético (Synthetic Monitoring Explained: A Guide to Reliable DevOps Workflows) simula usuários com scripts agendados, de várias regiões, e pega o caso “está no ar, mas inutilizável”. Comece por 3 a 5 jornadas críticas e alerte sobre sintomas que afetam o usuário (error budget queimando rápido), não sobre causas como CPU em 80%.

Git no dia a dia

Para começar O Git guarda cada mudança como um commit (uma foto do projeto) e permite linhas paralelas de trabalho (branches) que depois se juntam. Depois do básico, todo mundo esbarra em “minha branch ficou desatualizada” ou “preciso só daquele commit”.

O vídeo TUTORIAL GIT | Git Rebase, Git Cherry Pick, Git Ammend, Git Rebase Interativo apresenta quatro comandos:

  • git rebase main reaplica seus commits sobre a ponta da main, com novos hashes e histórico linear; o merge preserva a história com um merge commit (veja a figura a seguir). Para atualizar um PR: git fetch, git rebase origin/main, resolver conflitos, git rebase --continue e git push --force-with-lease.
  • git stash guarda o trabalho em andamento para atender um hotfix; stash pop o traz de volta.
  • git cherry-pick <hash> traz um commit específico.
  • git commit --amend refaz o último commit (também muda o hash).

Regra de ouro: nunca reescreva histórico público. Na sua própria branch, prefira --force-with-lease, que recusa o push se houver commits que você não viu. Outras práticas: PRs pequenos (algumas centenas de linhas), Conventional Commits, main protegida com CI obrigatório e git worktrees para trabalhar em várias branches ao mesmo tempo, hoje muito usados para rodar agentes de IA em paralelo (ver Livro 3, Capítulo 1, Programando com IA).

Você sabia? Linus Torvalds escreveu a primeira versão do Git em abril de 2005, em poucos dias, depois que o kernel Linux perdeu a licença gratuita do BitKeeper. “Git” é gíria britânica para pessoa teimosa e desagradável, e Torvalds brincou que batiza projetos em sua própria homenagem.

Começando do zero e modernizando o legado

O checklist de “dia 1” de Como Eu Começo Um Projeto do Zero: escolher a stack pelo objetivo (para ganhar dinheiro, use o que já domina; frameworks “baterias incluídas” como Django, Rails e Laravel ajudam o dev solo), planejar o MVP num documento no repositório, publicar o Hello World com CD, configurar migrações, pôr testes no pipeline e escrever README e AGENTS.md.

Código legado funciona, mas não tem testes, documentação nem quem entenda todas as regras, e os especialistas em COBOL estão se aposentando. O vídeo What Is Legacy Code? How AI Is Modernizing Legacy Systems defende modernização incremental. A IA acelera a descoberta, a tradução e a geração de testes, mas uma tradução sintaticamente correta pode se comportar errado; por isso o primeiro passo continua sendo cobrir o comportamento atual com testes de caracterização.

O ciclo de vida do software com IA

Os vídeos AI in the SDLC: Rethinking AI Coding Tools & AI Agents e What Is RAD? Why It Matters in the Age of AI Coding partem de um dado incômodo: num ensaio controlado da METR (2025), desenvolvedores experientes se sentiram ~20% mais rápidos com IA, mas foram ~20% mais lentos. Acelerar a digitação adianta pouco se o tempo vai para as esperas entre etapas e para revisar milhares de linhas não lidas. A superdelegação (“construa um e-commerce”) deixa decisões implícitas; a subdelegação desperdiça a ferramenta. O caminho é redesenhar o ciclo: spec-driven development no lugar do vibe coding, testes gerados a partir das histórias de usuário e métricas de resultado, não de linhas de código. O RAD de James Martin, dos anos 1980, já previa protótipos rápidos com o usuário; faltavam ferramentas, e os agentes agora as oferecem.

A revisão de código, segundo How AI Is Changing Code Reviews & Software Development, foi das inspeções formais de Michael Fagan na IBM, nos anos 1970, aos pull requests e agora à IA. O foco migrou de “como construímos?” para “construímos o que queríamos?”, com base em evidências: testes, checagens automáticas e dados de execução.

Em resumo Qualidade de implementação está ficando barata; qualidade de decisão é o diferencial. Diante de uma feature gerada por IA, pergunte: síncrona ou assíncrona? O que acontece se o serviço downstream cair? Quantos retries? E se os usuários passarem de 10 mil para 10 milhões? Este capítulo existe para que você saiba responder.
